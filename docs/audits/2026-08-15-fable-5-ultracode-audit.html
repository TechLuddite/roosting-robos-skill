Verdict: a genuinely well-engineered skill with no critical defects — but four high-severity issues, one of which means the product's headline install path is currently broken.

This repository is far above the bar for community Claude skills. The skill text is a model of progressive disclosure and degradation-path design; the packager rejects symlinks and builds reproducibly (both properties held under live attack-style testing); CI is SHA-pinned, least-privilege, and fail-closed; and the safety documentation is unusually honest about what behavioral guardrails can and cannot do. The audit's 65 recorded strengths are not padding — most repos of this kind would fail the tests this one passes.

The four high-severity findings cluster into three stories. First, the shipped release is dead: the v0.1.0 GitHub Release contains no rewst.skill asset because both CI runs on the tag failed under a since-fixed bug, so the documented claude.ai/desktop install path 404s in practice while the release body promises an auto-attached asset (release-01) — and because v0.1.0 is already consumed, the fix requires a version bump, not just a re-run (version-01). Second, the secret scanner over-promises: the validator that justifies committing the tenant manifest can be bypassed by a JWT pasted mid-string, by credentials under a secret-named list or dict, and by a nested value field — all reproduced live with exit-0 runs, twice, by independent agents (val-01, val-02, val-03). The fixes are small: the correct unanchored regex already exists in the file. Third, the prompt-security boundary is missing: the skill routes fetched docs, third-party AI answers, and tenant-authored text into sessions that write to production customer environments, yet no file says that content arriving through those channels is data rather than instructions, or that approvals only count when typed by the human (inj-01). For a skill whose own README concedes "the text IS the security layer," that is the single most important addition to make.

The eight medium findings are mostly claim-vs-reality gaps (README overstating validator coverage, the public-fork recipe not scrubbing history, the recommended plugin channel bypassing every CI gate the README advertises) plus the house-style precedence loophole. Everything below that is hardening and polish.

High val-01 Anchored value regex misses embedded secrets in valid JSON that the raw-scan fallback would catch skills/rewst/scripts/validate_manifest.py:43

Confirmed validate_manifest.py (static + dynamic)

For parsed manifests, string values are checked with SECRET_VALUE_PATTERN, which is the secret-prefix alternation anchored at start-of-string and applied with .match(). A secret that does not sit at position 0 of the value passes clean: 'Bearer eyJ...' (a JWT pasted with its Authorization-header prefix) and 'uses key AKIAIOSFODNN7EXAMPLE for S3 sync' both validate with exit 0. The unparseable-file fallback uses the identical alternation unanchored with .search(), so the exact same content in a syntactically broken file IS flagged — valid JSON gets strictly weaker secret scanning than invalid JSON, inverting the code's own stated intent that the secret check 'must not be skippable'. This file is designed to be committed to git, so these are real leak paths.

✓ Independently discovered and reproduced by the data-privacy auditor (originally tracked as man-01); both reproductions used the same Bearer-prefixed JWT and mid-string AKIA test cases.

Evidence

Line 43: `SECRET_VALUE_PATTERN = re.compile(r"^" + _SECRET_VALUE)` vs line 46: `SECRET_VALUE_ANYWHERE = re.compile(_SECRET_VALUE)`; line 101: `elif isinstance(val, str) and SECRET_VALUE_PATTERN.match(val.strip()):` vs line 84 (raw path): `if SECRET_VALUE_ANYWHERE.search(line):`. High val-02 Secret-named keys holding lists or dicts bypass the key-based check entirely skills/rewst/scripts/validate_manifest.py:98

Confirmed validate_manifest.py (static + dynamic)

walk_for_secrets only flags a secret-named key when its value is str/int/float. If the value is a list or dict, only the narrow value-prefix regex is applied to the leaves, so ordinary credentials under an explicitly secret-named container pass clean: {"passwords": ["hunter2", "letmein99"]} and {"credentials": {"user": "svc", "pass": "hunter2"}} both exit 0. This defeats the exact signal the scanner already recognized (the key name says 'password'/'credential') the moment the value is structured — a very common way credentials are transcribed from API responses.

Evidence

Lines 98-99: `if (SECRET_KEY_PATTERN.search(key) and isinstance(val, (str, int, float)) and not isinstance(val, bool) and str(val).strip()):`. Recommendation

When SECRET_KEY_PATTERN matches a key whose value is a list or dict, flag any non-empty string/number leaf underneath it (or simply flag the key itself as an error: a container named 'passwords'/'credentials' has no legitimate place in a names-and-types manifest).

Medium man-04 The git rm --cached recipe does not scrub history — a fork made public after a populated manifest was ever committed still exposes the full client map — and the recipe's commit never includes the .gitignore change README.md:126

Confirmed Data handling & privacy

The README's core claims are technically accurate (gitignore is indeed ignored for tracked files; the untrack sequence works going forward). But 'If the fork must be public, untrack them first' is only safe if run before any populated commit. A user who reads this section after refreshing and committing — the exact failure the paragraph describes ('the next git add . after a refresh commits the populated manifest anyway') — will run the recipe, see the files untracked, and publish a fork whose history still contains every customer org name/ID, integration ID, and PSA lookup. Verified by simulation: after running the README's exact commands, `git show HEAD~1:skills/rewst/references/tenant-manifest.json` returns the populated content. Minor secondary defect: `printf ... >> .gitignore` modifies the working tree but nothing stages it, so the commit labeled 'Keep tenant manifest and house style out of the public fork' does not contain the .gitignore entries (git status shows `?? .gitignore` after the commit); protection still works locally because git reads the working-tree .gitignore, but a collaborator's fresh clone of that commit has no ignore entries.

Evidence

README.md lines 126-131 (the recipe: `git rm --cached ... / printf '%s\n' ... >> .gitignore / git commit -m "Keep tenant manifest and house style out of the public fork"`). Simulation output: after the recipe, `git status --short` → '?? .gitignore'; `git show HEAD~1:skills/rewst/references/tenant-manifest.json` → '{"tenant":"org-real-tenant-9f2","orgs":[{"id":"org-acme-77","name":"Acme Corp Real Customer"}]}'.

Recommendation

Add one sentence after the recipe: 'If a populated version was ever committed, untracking is not enough — rewrite history (git filter-repo) or start from a fresh clone of upstream before making the fork public.' Add `git add .gitignore` (or `git commit -am`) so the ignore entries land in the same commit.
